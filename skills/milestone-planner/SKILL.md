# milestone-planner：里程碑规划

## 工作方式

基于 PRODUCT.md 的功能边界和已有里程碑的完成情况，规划下一个里程碑的内容范围。

## 输入

| 数据 | 路径 | 作用 | 必需 |
|------|------|------|------|
| 产品文档 | 默认 `docs/PRODUCT.md`，以 `AGENTS.md` 定义为准 | 功能边界、用户可见流程 | 是 |
| 开发设计文档 | 默认 `docs/DEVELOPMENT.md`，以 `AGENTS.md` 定义为准 | 已规划的里程碑列表 | 否 |
| 已完成里程碑 | `docs/milestones/` 目录 | 确定已完成的版本号和功能 | 否 |
| 项目版本 | `package.json` 等项目文件 | 版本号参考（实际递增以已完成里程碑为准） | 否 |

**前置检查**：如果产品文档缺失，提示用户先创建再执行。

## 规划原则

按照以下优先级排序，确保项目从底层到上层、核心到周边、通用到特用逐步构建：

1. **底层到上层**：先做数据层、基础设施，再做业务逻辑，最后做 UI 层
2. **核心到周边**：先做核心功能，再做辅助功能
3. **通用到特用**：先做通用组件/服务，再做特定场景的功能

## 功能状态标记约定

`PRODUCT.md` 的功能列表是产品规格（持久不变，功能建成后仍保留在规格中）。为避免已规划/已完成/已放弃的功能被反复选入里程碑，每个功能项需带状态标记。**本技能是 `PRODUCT.md` 功能状态标记的唯一写入方**，在规划时同步维护，dev-flow 不修改 `PRODUCT.md`。

状态取值（标注在功能项前或行尾，如 `- [待规划] 用户登录`）：

| 状态 | 含义 | milestone-planner 对待 |
|------|------|------------------------|
| `[待规划]` | 尚未纳入任何里程碑（**缺省值**：无标记的功能项默认视为待规划） | 候选，可被选入下一个里程碑 |
| `[已规划]` | 已纳入某个里程碑，但对应里程碑尚未完成 | 不重复选入（避免范围重叠） |
| `[已完成]` | 覆盖该功能里程碑已完成 | 永不选入 |
| `[已放弃]` | 团队决定不做 / 长期不打算做 | 永不选入（功能项保留在规格中以示决策，不被物理删除） |

## 执行步骤

1. 读取 PRODUCT.md 的功能列表，获取每项状态（无标记视为 `[待规划]`）
2. 读取 DEVELOPMENT.md（如有），获取已规划的里程碑列表
3. 读取 `docs/milestones/` 目录，确定已完成的里程碑和功能；将已被**已完成**里程碑覆盖的功能在 `PRODUCT.md` 中标记为 `[已完成]`（若原本为 `[已规划]` 则覆盖）。此同步确保 `PRODUCT.md` 状态与 `docs/milestones/` 实际完成情况一致
4. 读取 `docs/BUGS.md` 缺陷池（若存在），收集"留到下个版本"的待处理 bug。这些 bug 由 `dev-bug` 在判定明显越界时归入，是下个里程碑的候选修复项
5. 确定版本号：读取 `docs/milestones/` 中已有里程碑，按标识取最大者作为基准。标识风格沿用项目已有里程碑：语义版本风格取最大 `vX.Y.Z`（如 `v1.2.0`），序号风格取最大 `M{数字}`（如 `M30`）；如无任何已完成里程碑，默认从语义版本 `v0.1.0` 开始。`package.json` 等版本仅作参考
6. 确定递增类型：根据里程碑内容判断 patch/minor/major
   - **patch**：bug 修复、重构、文档更新，无新功能
   - **minor**：新增功能，向后兼容（里程碑默认递增方式，如 v0.9.0 → v0.10.0 或 M30 → M31）
   - **major**：破坏性变更（如 v0.x.x → v1.0.0）
7. 基于规划原则，从 `PRODUCT.md` 的功能列表中选取下一个里程碑的功能范围。**仅从 `[待规划]` 状态的功能项中选取**（已规划/已完成/已放弃均不选入，避免范围重叠或重复规划）；选取后将该功能项在 `PRODUCT.md` 标记为 `[已规划]`。若 `docs/BUGS.md` 缺陷池非空，优先将其中高优先级（🔴/🟡）的 bug 纳入本里程碑的修复范围，并在子任务中体现；若缺陷池内容构成里程碑主体（无新功能、仅修复），则该里程碑版本类型判定为 patch
   - **缺陷池消费**：被本步骤纳入里程碑的 bug，**必须同时从 `docs/BUGS.md` 删除对应行**（它已转入本里程碑文档的 `## Bugs` 表，由 dev-flow 步骤3 跟踪修复）。未被纳入的低优先级（🟢）或其他 bug 保留在池子中，供后续里程碑规划。池子清空后保留文件头（空表）即可，不必删除文件
8. 一个里程碑聚焦一个核心功能，避免范围过大
9. 将规划结果写入 DEVELOPMENT.md：
   - 若 DEVELOPMENT.md 中已存在 `## 里程碑划分` 标题，**不要重复复制该标题**，直接在其下方追加新的里程碑条目（避免随规划次数增多出现多个同名段落）
   - 若 DEVELOPMENT.md 为空或未定义该标题，则新建 `## 里程碑划分` 标题再追加条目
10. **提示用户确认规划内容**，等待用户确认后再完成

## 输出

更新 `docs/DEVELOPMENT.md`，追加新里程碑条目。输出格式如下：

```markdown
## 里程碑划分

### v1.0.0 基础架构 ✅
- **核心功能**：搭建项目骨架、目录结构、开发环境
- **子任务**：5 个（项目初始化、前端环境、后端环境、测试配置、文档）

### v1.1.0 用户管理 ← 新增（下一步）
- **核心功能**：用户 CRUD API 和前端管理页面
- **子任务**：5 个（用户模型、CRUD API、前端列表页、前端表单页、单元测试）
- **依赖**：v1.0.0 基础架构
- **版本类型**：minor
- **版本号**：v1.1.0

### v1.1.1 修复用户管理已知问题
- **核心功能**：修复用户列表分页错误、重构用户验证逻辑
- **子任务预估**：3 个（修复分页 bug、重构验证逻辑、补充测试）
- **依赖**：v1.1.0 用户管理
- **版本类型**：patch
- **版本号**：v1.1.1

### v1.2.0 权限管理
- **核心功能**：基于角色的访问控制（RBAC）
- **子任务预估**：5-6 个（角色模型、权限模型、权限中间件、前端权限页面、路由守卫）
- **依赖**：v1.1.0 用户管理（需要用户-角色关联）
- **版本类型**：minor
- **版本号**：v1.2.0
```

状态标记：✅ 已完成 / 🔄 当前 / ← 新增（下一步）/ 无标记（未开始）

**识别约定**：`← 新增（下一步）` 标记代表"下一个待做里程碑"，是 dev-flow 步骤1 读取"下一个里程碑"的唯一依据。dev-flow 步骤8 完成本里程碑后，会将其标记改为 `✅ 已完成`，并把下一个待做里程碑标记前移为 `← 新增（下一步）`。本技能再次运行时只能规划 `← 新增（下一步）` 之后的新里程碑，不会重复已存在的条目。

每个里程碑条目包含：
- **核心功能**：一句话描述本里程碑的主要功能
- **子任务**（已完成）或**子任务预估**（新增）：子任务数量和方向
- **依赖**：前置里程碑和依赖关系
- **版本类型**：patch / minor / major（新增条目）
- **版本号**：完整版本号（新增条目）

## 约束

- 一次只规划一个里程碑，不一次性规划所有后续里程碑
- 每个里程碑聚焦一个核心功能，子任务控制在 3-8 个
- 不跳过必要的基础设施（如数据库、认证）直接做业务功能
- 必须等待用户确认后才算完成
