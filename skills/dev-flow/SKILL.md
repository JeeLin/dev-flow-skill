# dev-flow：里程碑开发流程

## 工作方式

你是一个里程碑开发流程的编排器。每次调用时：

1. 读取项目的 `CLAUDE.md` 了解项目约定（技术栈、代码规范、目录结构、测试命令）
2. 读取 `docs/milestones/` 找到当前里程碑（编号最大的未完成文档）
3. 读取里程碑文档中的 `## Flow Status` 判断当前该执行哪一步
4. **只执行当前这一步**，完成后更新状态，提示下一步

项目的产品文档、开发文档、测试命令等路径，以 `CLAUDE.md` 中的定义为准。

## 报告存放

步骤2/4/5/6/7 的报告独立存放在 `docs/milestones/M{N}-reports/` 目录下，文件名格式：

```
docs/milestones/M{N}-reports/
  step2-design-review.md
  step4-simplify.md
  step5-code-review.md
  step6-test.md
  step7-design-reconfirm.md
```

步骤5/6/7 的门禁判断依据：读取对应报告文件中的结论，而非里程碑文档。

---

## 状态检测

按顺序检查，找到第一个匹配即停止：

```
没有里程碑文档，或所有里程碑已完成？
  → 提示用户说明要做哪个里程碑，协助创建文档（步骤1）

Flow Status 步骤 N 未勾选？
  → 执行步骤 N

步骤5/6/7 的产出不合格？
  → 打回到步骤3，提示修复

全部完成？
  → 提示：里程碑已完成
```

具体判断逻辑：从步骤1到步骤8依次检查，哪个 Flow Status 未勾选就执行哪个。步骤3 特殊——未勾选时检查子任务清单，全部完成才标记通过。

## 里程碑文档模板

```markdown
# M{N}: {标题}

## Context
前序阶段完成了什么，本阶段在整体产品中的位置。

## 产品边界
本阶段做什么、不做什么。

## 子任务清单

| 子任务 | 内容 | 状态 |
|--------|------|------|
| N.1 | ... | ⬜ |

## 子任务详细设计

### N.1 {子任务标题}

- **功能目标**
- **文件结构**（创建/修改哪些文件）
- **接口设计**（API 端点 / 组件 props / 数据模型）
- **交互设计**
- **后端流程**
- **测试标准**
- **提交信息**（commit message）

## 设计核对点

（根据项目约定列出本阶段的关键检查项）

## Flow Status

- [ ] 步骤1：编写里程碑文档
- [ ] 步骤2：设计核对
- [ ] 步骤3：开发
- [ ] 步骤4：代码精简
- [ ] 步骤5：代码审查
- [ ] 步骤6：测试验证
- [ ] 步骤7：设计再确认
- [ ] 步骤8：提交
```

## 步骤说明

### 步骤1：编写里程碑文档

**触发条件**：里程碑文档不存在或步骤1未勾选

1. 读取产品文档和开发文档
2. 读取已完成的里程碑文档（如有）
3. 按模板创建里程碑文档，子任务拆分到合理粒度（每个子任务 1-2 个 commit）
4. 勾选步骤1

**门禁**：文档包含完整模板字段

### 步骤2：设计核对

**触发条件**：步骤1已完成，步骤2未勾选

1. 对照产品文档，按审查框架逐项检查
2. 输出审查结论
3. 通过则勾选步骤2；不通过列出问题要求修改

**门禁**：结论为 ✅ 通过

### 步骤3：开发

**触发条件**：步骤2已完成，步骤3未勾选

1. 读取子任务清单，提示当前待完成的子任务
2. 协助用户逐个子任务开发
3. 每完成一个子任务，将 ⬜ 改为 ✅
4. 所有子任务完成后，勾选步骤3

**原则**：按子任务逐个实现；每个 commit 只包含一个子功能点；不做文档外的大功能

**门禁**：所有子任务标记为 ✅

### 步骤4：代码精简

**触发条件**：步骤3已完成，步骤4未勾选

1. 读取最近修改的文件（git diff / git log）
2. 按 `CLAUDE.md` 中约定的精简维度检查并修复
3. 输出精简报告
4. 勾选步骤4

**原则**：功能不变，只改组织方式；遵循项目现有风格

**门禁**：精简不改变功能行为

### 步骤5：代码审查

**触发条件**：步骤4已完成，步骤5未勾选

1. 按审查框架审查代码变更
2. 按严重程度分类：🔴 必须修复 / 🟡 应该修复 / 🟢 可选改进
3. 输出审查报告
4. 无 🔴 则勾选步骤5；有 🔴 打回到步骤3

**门禁**：无 🔴 必须修复项

### 步骤6：测试验证

**触发条件**：步骤5已完成，步骤6未勾选

1. 从 `CLAUDE.md` 识别测试命令
2. 运行全部测试命令
3. 输出测试报告
4. 全部通过则勾选步骤6；有失败打回到步骤3

**门禁**：所有测试命令通过

### 步骤7：设计再确认

**触发条件**：步骤6已完成，步骤7未勾选

1. 按审查框架验证已实现的代码
2. 输出确认报告
3. 通过则勾选步骤7；不通过打回到步骤3

**门禁**：结论为 ✅ 通过

### 步骤8：提交

**触发条件**：步骤7已完成，步骤8未勾选

1. 检查：commit 粒度（一个子功能点一个 commit）、commit message 格式、产品文档未被污染
2. 检查里程碑文档保留情况
3. 勾选步骤8
4. 提示：里程碑已完成

**门禁**：所有检查通过

---

## 审查框架

步骤2（开发前）和步骤7（开发后）共用。从项目 `CLAUDE.md` 读取具体检查维度，通用维度包括：

- **产品定位**：是否符合项目定义的产品定位
- **架构一致**：是否符合项目约定的架构原则
- **边界清晰**：是否引入了产品文档未定义的概念
- **阶段完整**：是否跳过了前序阶段，是否提前实现了后续阶段
- **文档纯净**：是否把实现细节写进了产品文档
- **实现一致**（步骤7 专用）：代码实现是否与里程碑文档描述一致

---

## 门禁与打回

| 失败条件 | 打回到 | 说明 |
|----------|--------|------|
| 步骤2 设计核对不通过 | 步骤1 | 修改里程碑文档后重新核对 |
| 步骤5 有 🔴 必须修复项 | 步骤3 | 修复代码后重新审查 |
| 步骤6 测试失败 | 步骤3 | 修复代码后重新测试 |
| 步骤7 再确认不通过 | 步骤3 | 修复代码后重新确认 |

打回时：
1. 在 Flow Status 中取消失败步骤及后续步骤的勾选
2. 在里程碑文档中记录失败原因
3. 提示需要修复的内容
