# dev-flow：里程碑开发流程

## 工作方式

你是里程碑开发流程的编排器。每次调用时，先读取基础数据，再进入状态机判断当前该做什么。

### 循环与上下文管理

循环执行和上下文压缩通过 Claude Code 的内置命令实现，技能本身不包含循环逻辑：

- **连续执行**：使用 `/loop 5m /dev-flow` 每 5 分钟自动调用一次，技能每次从里程碑文档读取状态，自动执行下一步
- **上下文压缩**：使用 `/loop 30m /compact` 定期压缩上下文，避免对话过长
- **手动恢复**：上下文截断后直接调用 `/dev-flow`，状态机从里程碑文档的 Flow Status 恢复进度

关键原则：所有状态写入里程碑文档，不依赖对话记忆。无论上下文如何变化，重新调用 `/dev-flow` 都能从文档中恢复。

## 基础数据

每次执行流程前，必须读取：

| 数据 | 路径 | 作用 |
|------|------|------|
| 项目约定 | `CLAUDE.md` | 技术栈、代码规范、目录结构、测试命令、审查维度 |
| 产品文档 | 默认 `docs/PRODUCT.md`，以 `CLAUDE.md` 定义为准 | 产品定位、功能边界、用户可见流程 |
| 开发设计文档 | 默认 `docs/DEVELOPMENT.md`，以 `CLAUDE.md` 定义为准 | 整体规划、里程碑划分、架构决策 |
| 原型代码 | 默认 `prototype/`，以 `CLAUDE.md` 定义为准 | 前端交互参考、UI 布局参考 |

## 状态机

按顺序匹配，命中第一个即执行。每次调用执行一个步骤，执行完即停止。连续执行通过 `/loop` 命令实现。

状态机以里程碑文档的 Flow Status 为准。如果 Flow Status 显示某步骤已完成，但实际子任务状态不一致（如步骤3已勾选但子任务仍有 ⬜），以 Flow Status 为准继续推进，不回头补做。

```
IF 没有里程碑文档，或全部已完成
  → 步骤1：创建新里程碑

ELSE 找到当前里程碑（docs/milestones/ 中版本号最大的未完成文档）
  读取其 ## Flow Status：

  IF 步骤1 已勾选，但步骤2 未勾选，且里程碑文档打回记录表格有非空行
    → 取消步骤1及后续勾选，进入步骤1：根据打回记录重新编写

  IF 步骤1 未勾选
    → 步骤1：编写里程碑文档

  IF 步骤2 未勾选
    → 步骤2：设计核对

  IF 步骤3 未勾选
    → 步骤3：开发（按子任务逐个执行）

  IF 步骤4 未勾选
    → 步骤4：代码精简

  IF 步骤5 未勾选
    → 步骤5：代码审查（执行后检查报告，有 🔴 则打回）

  IF 步骤6 未勾选
    → 步骤6：测试验证（执行后检查报告，有失败项则打回）

  IF 步骤7 未勾选
    → 步骤7：设计再确认（执行后检查报告，结论为 ❌ 则打回）

  IF 步骤8 未勾选
    → 步骤8：提交

  全部完成
    → 提示：里程碑已完成，可以开始下一个
```

## 里程碑文档

### 位置

默认 `docs/milestones/{version}-{name}.md`（如 `v1.0.0-基础架构.md`），项目 `CLAUDE.md` 可覆盖。

### 模板

```markdown
# {version}: {标题}

## Context
前序阶段完成了什么，本阶段在整体产品中的位置。
版本类型：minor（默认）/ patch（小修复）/ major（重大变更）

## 产品边界
本阶段做什么、不做什么。

## 子任务清单

| # | 内容 | 状态 |
|---|------|------|
| 1 | ... | ⬜ |
| 1a | ...（子编号，可选） | ⬜ |
| 2 | ... | ⬜ |

## 子任务详细设计

### 1 {子任务标题}

- **功能目标**
- **文件结构**（创建/修改哪些文件）
- **接口设计**（API 端点 / 组件 props / 数据模型）
- **交互设计**（参考原型代码）
- **后端流程**
- **测试标准**
- **提交信息**（commit message）

## 设计核对点

（根据项目约定列出本阶段的关键检查项）

## Flow Status

- [ ] 步骤1：编写里程碑文档
- [ ] 步骤2：设计核对
- [ ] 步骤3：开发
- [ ] 步骤4：代码精简
- [ ] 步骤5：代码审查
- [ ] 步骤6：测试验证
- [ ] 步骤7：设计再确认
- [ ] 步骤8：提交

## 打回记录

（打回时追加一条，创建里程碑时留空）

| 时间 | 步骤 | 原因 |
|------|------|------|
| | | |
```

子任务编号规则：主编号用数字（1, 2, 3），需要拆分时用字母子编号（1a, 1b）。子任务清单和详细设计中的编号必须一一对应。

## 报告

步骤2/4/5/6/7 的报告存放在 `docs/milestones/{version}-reports/` 目录下：

| 步骤 | 文件名 | 内容 |
|------|--------|------|
| 2 | `step2-design-review.md` | 里程碑文档 vs 产品文档的审查结论 |
| 4 | `step4-simplify.md` | 代码精简检查结果 |
| 5 | `step5-code-review.md` | 代码审查发现和严重程度分级 |
| 6 | `step6-test.md` | 测试命令运行结果和覆盖率 |
| 7 | `step7-design-reconfirm.md` | 代码实现 vs 里程碑文档的确认结论 |

步骤说明中的 `{version}-reports/` 路径均相对于 `docs/milestones/`。

步骤5/6/7 的门禁判断依据是对应报告文件中的结论。

---

## 审查框架

步骤2和步骤7共用审查框架，但检查对象不同：

- **步骤2（开发前）**：检查里程碑文档 vs 产品文档，验证设计是否合理
- **步骤7（开发后）**：检查已实现代码 vs 里程碑文档，验证实现是否正确

`CLAUDE.md` 中定义的审查维度在此两个阶段均纳入检查。

---

## 门禁与打回

| 步骤 | 门禁条件 | 不通过时 |
|------|----------|----------|
| 1 | 文档包含完整模板字段 | 重新编写 |
| 2 | 报告结论为 ✅ | 小问题：Claude 直接修改文档重新核对；大问题：打回到步骤1 |
| 3 | 所有子任务标记为 ✅ | 继续开发 |
| 4 | 精简不改变功能行为 | 回退改动 |
| 5 | 审查报告无 🔴 | 取消步骤5勾选，用户修复后重入步骤5 |
| 6 | 测试报告全部通过 | 取消步骤6勾选，用户修复后重入步骤6 |
| 7 | 确认报告结论为 ✅ | 取消步骤7勾选，用户修复后重入步骤7 |
| 8 | 所有检查通过 | 修复后重新检查 |

打回动作（步骤2）：
- 小问题（措辞、细节缺失）：Claude 直接修改里程碑文档，保持步骤1勾选，重新执行步骤2
- 大问题（设计方向错误、产品边界不合理、子任务拆分粒度不当）：取消步骤1及后续勾选，在里程碑文档的"打回记录"表格中追加一行，重新进入步骤1

打回动作（步骤5/6/7）：
1. 取消失败步骤及后续步骤的 Flow Status 勾选
2. 在里程碑文档的"打回记录"表格中追加一行
3. 执行文件操作：将失败步骤的报告文件重命名，原文件名加 `.rejected` 后缀（如 `step5-code-review.md` → `step5-code-review.md.rejected`），避免状态机重新匹配到旧报告
4. 将详细发现摘要记录到打回记录中
5. 提示用户需要修复的内容

## 步骤详细说明

### 步骤1：编写里程碑文档

**触发条件**：Flow Status 步骤1 未勾选

1. 读取产品文档、开发文档、原型代码
2. 读取已完成的里程碑文档（如有），确定当前版本号
3. 确定新里程碑版本号：在当前版本号基础上递增 minor（如 v1.0.0 → v1.1.0），除非 Context 明确标注 patch 或 major
4. 按模板创建里程碑文档，子任务拆分到 1-2 个 commit 的粒度
5. 勾选步骤1

**门禁**：文档包含完整模板字段（Context、产品边界、子任务清单与详细设计、设计核对点、Flow Status、打回记录）

**打回场景**：步骤2审查发现设计方向错误、产品边界不合理、子任务拆分粒度不当等大问题时，会取消步骤1勾选并打回到此步骤。此时根据里程碑文档中"打回记录"表格的记录重新编写文档。重写完成后清空打回记录表格，避免状态机重复触发。

### 步骤2：设计核对

**触发条件**：步骤1已完成，Flow Status 步骤2 未勾选

1. 按审查框架的步骤2维度逐项检查里程碑文档
2. 报告写入 `{version}-reports/step2-design-review.md`
3. 通过 → 勾选步骤2
4. 不通过 → 按问题严重程度处理：
   - **小问题**（措辞不准确、细节缺失）：Claude 直接修改里程碑文档，保持步骤1勾选，重新执行步骤2。最多修正 3 次仍不通过，视为大问题
   - **大问题**（设计方向错误、产品边界不合理、子任务拆分粒度不当）：取消步骤1及后续勾选，在里程碑文档的"打回记录"表格中追加一行，提示用户需要重新设计

**门禁**：报告结论为 ✅

### 步骤3：开发

**触发条件**：步骤2已完成，Flow Status 步骤3 未勾选

1. 读取里程碑文档中的子任务清单和详细设计
2. 找到下一个未完成的子任务（⬜），按详细设计实现代码
3. 每完成一个子任务，立即更新状态（⬜ → ✅）并提交
4. 检查是否还有未完成子任务，有则回到第2步继续
5. 所有子任务完成 → 勾选步骤3

**原则**：按子任务逐个实现；每个 commit 只包含一个子功能点；不做文档外的大功能；参考原型代码确认交互细节

**门禁**：所有子任务标记为 ✅

### 步骤4：代码精简

**触发条件**：步骤3已完成，Flow Status 步骤4 未勾选

1. 读取最近修改的文件（git diff / git log）
2. 按 `CLAUDE.md` 中约定的维度检查并修复
3. 精简报告写入 `{version}-reports/step4-simplify.md`
4. 勾选步骤4

**原则**：功能不变，只改组织方式；遵循项目现有风格

**门禁**：精简不改变功能行为

### 步骤5：代码审查

**触发条件**：步骤4已完成，Flow Status 步骤5 未勾选

1. 按审查框架审查代码变更（见下方审查框架）
2. 分类：🔴 必须修复 / 🟡 应该修复 / 🟢 可选改进
3. 审查报告写入 `{version}-reports/step5-code-review.md`
4. 无 🔴 → 勾选步骤5；有 🔴 → 打回到步骤3

**门禁**：审查报告无 🔴 必须修复项

### 步骤6：测试验证

**触发条件**：步骤5已完成，Flow Status 步骤6 未勾选

1. 从 `CLAUDE.md` 识别测试命令并运行
2. 测试报告写入 `{version}-reports/step6-test.md`
3. 全部通过 → 勾选步骤6；有失败 → 打回到步骤3

**门禁**：测试报告全部通过

### 步骤7：设计再确认

**触发条件**：步骤6已完成，Flow Status 步骤7 未勾选

1. 按审查框架的步骤7维度验证已实现的代码
2. 确认报告写入 `{version}-reports/step7-design-reconfirm.md`
3. 通过 → 勾选步骤7；不通过 → 打回到步骤3

**门禁**：确认报告结论为 ✅

### 步骤8：提交

**触发条件**：步骤7已完成，Flow Status 步骤8 未勾选

1. 检查：commit 粒度（一子功能点一 commit）、commit message 格式、产品文档未被污染
2. 更新项目文件中的版本号（见版本管理）
3. 勾选步骤8
4. 提交里程碑文档和所有报告文件到 git：`git add docs/milestones/ && git commit -m "docs: milestone {version} completed"`

**门禁**：所有检查通过

### 版本管理

版本号在步骤1 确定并写入里程碑文档，步骤8 负责更新项目文件中的版本号：

| 项目类型 | 检测文件 | 更新命令 |
|----------|----------|----------|
| JavaScript/TypeScript | `package.json` | `bun version patch/minor/major`（优先 bun，无 bun 时回退到 npm） |
| Rust | `Cargo.toml` | 手动修改，或使用 `cargo-release` |
| Python | `pyproject.toml` / `setup.cfg` | 手动修改 |

步骤1 确定版本号规则：读取项目文件中的当前版本号，递增 minor（如 v1.0.0 → v1.1.0）。里程碑文档 Context 段落标注 patch 或 major 时按标注执行。
