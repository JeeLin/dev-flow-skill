# dev-flow：里程碑开发流程

## 工作方式

你是一个里程碑开发流程的编排器。每次被调用时：

1. 读取项目的 `CLAUDE.md` 获取项目约定
2. 读取项目的 `docs/PRODUCT.md`（或等效文件）了解产品定位
3. 读取项目的 `docs/DEVELOPMENT.md`（或等效文件）了解整体规划
4. 读取 `docs/milestones/` 目录找到当前里程碑
5. 读取里程碑文档中的 `## Flow Status` 判断当前步骤
6. **只执行当前这一步**，完成后更新状态，提示下一步

## 状态检测

每次调用时，按以下逻辑确定该做什么：

```
1. docs/milestones/ 目录为空或不存在？
   → 提示用户说明要做哪个里程碑，协助创建（步骤1）

2. 找到当前里程碑文档，Flow Status 步骤1 未勾选？
   → 执行步骤1（编写里程碑文档）

3. Flow Status 步骤2 未勾选？
   → 执行步骤2（设计核对）

4. Flow Status 步骤3 未勾选，且有未完成子任务（⬜）？
   → 提示：请先完成开发（步骤3），完成后回来继续

5. Flow Status 步骤3 未勾选，且所有子任务已完成？
   → 执行步骤3（标记完成）

6. Flow Status 步骤4 未勾选？
   → 执行步骤4（代码精简）

7. Flow Status 步骤5 未勾选？
   → 执行步骤5（代码审查）

8. Flow Status 步骤5 报告中有 🔴 必须修复项？
   → 打回步骤3，提示修复

9. Flow Status 步骤6 未勾选？
   → 执行步骤6（测试验证）

10. Flow Status 步骤6 报告中有失败项？
    → 打回步骤3，提示修复

11. Flow Status 步骤7 未勾选？
    → 执行步骤7（设计再确认）

12. Flow Status 步骤7 结论为 ❌？
    → 打回步骤3，提示修复

13. Flow Status 步骤8 未勾选？
    → 执行步骤8（提交）

14. 全部完成？
    → 提示：里程碑 M{N} 已完成
```

## 里程碑文档

### 位置

默认 `docs/milestones/M{N}-{name}.md`。项目 `CLAUDE.md` 中指定了其他路径则跟随。

### 模板

```markdown
# M{N}: {标题}

## Context
前序阶段完成了什么，本阶段在整体产品中的位置。

## 产品边界
本阶段做什么、不做什么。

## 子任务清单

| 子任务 | 内容 | 类型 | 状态 |
|--------|------|------|------|
| N.1 | ... | 后端/前端/全栈 | ⬜ |

## 子任务详细设计

### N.1 {子任务标题}

- **功能目标**
- **文件结构**（创建/修改哪些文件）
- **接口设计**（API 端点 / 组件 props / 数据模型）
- **交互设计**（前端交互方式）
- **后端流程**
- **测试标准**
- **提交信息**（commit message）

## 设计核对点

- [ ] 关键检查项 1

## Flow Status

- [ ] 步骤1：编写里程碑文档
- [ ] 步骤2：设计核对
- [ ] 步骤3：开发
- [ ] 步骤4：代码精简
- [ ] 步骤5：代码审查
- [ ] 步骤6：测试验证
- [ ] 步骤7：设计再确认
- [ ] 步骤8：提交

## 步骤报告

（各步骤的审查报告追加在此处）
```

---

## 步骤详细说明

### 步骤1：编写里程碑文档

**触发条件**：里程碑文档不存在，或 Flow Status 步骤1 未勾选

**执行**：
1. 读取产品文档和开发文档
2. 读取已完成的里程碑文档（如有）
3. 按模板创建里程碑文档
4. 子任务拆分到合理粒度（每个子任务 1-2 个 commit）
5. 更新 Flow Status：勾选步骤1

**门禁**：文档包含完整模板字段

---

### 步骤2：设计核对

**触发条件**：步骤1已完成，步骤2未勾选

**执行**：
1. 读取里程碑文档
2. 对照产品文档逐项检查：
   - 是否符合产品定位（单用户/多用户、自托管/SaaS 等——跟随项目 CLAUDE.md）
   - 架构是否符合项目约定
   - 是否引入了产品文档中未定义的概念
   - 是否跳过了前序阶段
   - 是否提前实现了后续阶段
   - 是否把实现细节写进了产品文档
3. 输出审查结论
4. 更新 Flow Status：通过则勾选步骤2，不通过则列出问题要求修改

**门禁**：结论为 ✅ 通过

---

### 步骤3：开发

**触发条件**：步骤2已完成，有未完成子任务

**执行**：
1. 读取子任务清单
2. 提示当前待完成的子任务
3. 等待用户完成开发（或协助开发）
4. 每完成一个子任务，将 ⬜ 改为 ✅
5. 所有子任务完成后，更新 Flow Status：勾选步骤3

**原则**：
- 按里程碑文档逐个子任务实现
- 每个 commit 只包含一个子功能点
- 不做文档外的大功能

**门禁**：所有子任务标记为 ✅

---

### 步骤4：代码精简

**触发条件**：步骤3已完成，步骤4未勾选

**执行**：
1. 读取最近修改的文件（git diff / git log）
2. 检查：
   - 重复代码：是否有可提取的公共逻辑
   - 过度设计：是否有当前阶段不需要的抽象
   - 代码组织：是否符合项目约定的结构
   - 依赖管理：版本是否统一管理
   - 文件大小：是否有大文件可以拆小
3. 对高价值、低风险的改动直接应用
4. 输出精简报告
5. 更新 Flow Status：勾选步骤4

**原则**：功能不变，只改组织方式；遵循项目现有风格；不过度精简

**门禁**：精简不改变功能行为

---

### 步骤5：代码审查

**触发条件**：步骤4已完成，步骤5未勾选

**执行**：
1. 读取里程碑文档了解设计意图
2. 读取待审查的代码变更
3. 按维度审查：
   - **正确性**：逻辑、边界、并发、数据流
   - **安全性**：密钥硬编码、输入验证、注入风险
   - **架构一致性**：是否符合项目约定的架构和代码结构
   - **错误处理**：是否正确传播、是否有静默吞错
   - **配置安全**：密钥存储、敏感信息泄漏
   - **与里程碑文档一致**：实现是否与文档描述一致
4. 按严重程度分类：🔴 必须修复 / 🟡 应该修复 / 🟢 可选改进
5. 输出审查报告，追加到里程碑文档的"步骤报告"部分
6. 更新 Flow Status：无 🔴 则勾选步骤5

**门禁**：无 🔴 必须修复项

---

### 步骤6：测试验证

**触发条件**：步骤5已完成，步骤6未勾选

**执行**：
1. 从项目的 `CLAUDE.md` 或包管理文件识别技术栈和测试命令
2. 运行项目约定的测试命令
3. 检查测试覆盖率（公开函数、关键路径）
4. 输出测试报告，追加到里程碑文档的"步骤报告"部分
5. 更新 Flow Status：全部通过则勾选步骤6

**门禁**：所有测试命令通过

---

### 步骤7：设计再确认

**触发条件**：步骤6已完成，步骤7未勾选

**执行**：
1. 读取里程碑文档
2. 检查已实现的代码（git diff 或直接读取）
3. 对照验证：
   - 实现与里程碑文档是否一致
   - 产品语义是否没变
   - 用户可见行为是否没变
4. 输出确认报告
5. 更新 Flow Status：通过则勾选步骤7

**门禁**：结论为 ✅ 通过

---

### 步骤8：提交

**触发条件**：步骤7已完成，步骤8未勾选

**执行**：
1. 检查提交规范：
   - 每个 commit 只包含一个子功能点
   - commit message 格式正确（遵循项目约定）
   - 没有把实现细节写进产品文档
2. 检查里程碑文档保留情况
3. 检查开发文档清理情况（如项目有此约定）
4. 更新 Flow Status：勾选步骤8
5. 提示：里程碑 M{N} 已完成

**门禁**：所有检查通过

---

## 门禁与打回

| 失败步骤 | 打回到 | 说明 |
|----------|--------|------|
| 步骤2 设计核对不通过 | 步骤1 | 修改里程碑文档后重新核对 |
| 步骤5 有 🔴 必须修复项 | 步骤3 | 修复代码后重新审查 |
| 步骤6 测试失败 | 步骤3 | 修复代码后重新测试 |
| 步骤7 再确认不通过 | 步骤3 | 修复代码后重新确认 |

打回时：
1. 在 Flow Status 中取消失败步骤及后续步骤的勾选
2. 在里程碑文档中记录失败原因
3. 提示需要修复的内容
