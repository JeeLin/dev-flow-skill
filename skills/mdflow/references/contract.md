# 跨技能契约（contract.md）

本文件是 mdflow 技能集的**唯一契约源**。子技能（mdflow-review、mdflow-acceptance、mdflow-bug、mdflow-planner）只引用本文件的定义，不重复书写；各入口可补充**本入口特有的判定关键词**，但不得改变以下核心定义。修改本文件后必须运行 `scripts/check.sh`。

## 严重度分级契约

三档严重度（🔴🟡🟢）语义由本节统一定义：

| 级别 | 含义 | 在本流程中的处置 |
|------|------|------------------|
| 🔴 必须修复 | 阻断性问题：崩溃/数据丢失/安全漏洞/逻辑错误/破坏性变更/违反核心规范/接口报错/阻塞性问题 | 登记入当前里程碑 Bugs 表（⬜），轮末统一打回步骤3，下轮整轮重跑 4→5→6→7 |
| 🟡 应该修复 | 非阻塞性功能异常或质量缺陷：偶发/性能/可维护性差/命名不规范/体验问题 | 处置同 🔴 |
| 🟢 可选改进 | 锦上添花/轻微问题：风格优化/次要重构/建议优化 | 处置与 🔴/🟡 一致，本里程碑内解决，不推迟到下个版本 |

**核心约束**：三档发现即登记入当前里程碑 Bugs 表（⬜），均在本里程碑内解决（处理顺序 🔴→🟡→🟢）。步骤4/5/6/7 的发现在审查轮内登记、轮末统一打回；mdflow-bug 等其他入口登记的 bug 由状态机回到步骤3（审查轮进行中则先跑完本轮，随轮末统一打回一并处理）。没有「🟢 入缺陷池、下个版本处理」的例外。

**校准样例**（定级分歧以本节为准）：

- 🔴：上传接口未校验文件类型，可上传任意脚本执行（安全漏洞）；库存扣减无并发控制导致超卖（数据错误）
- 🟡：列表接口 N+1 查询，千条数据响应 3 秒（性能）；表单校验缺失，错误提示不可读（体验问题）
- 🟢：日志文案措辞不一致（风格）；两处重复常量定义可提取（轻微重构）
- **边界**：与本里程碑无关的纯文档笔误不登记、随下次文档提交顺手修；属于本里程碑交付内容的文档错误按 🟢 登记；「可能有用但没有依据的优化想法」不登记——发现必须基于当前代码事实。

## 发现登记格式

每条发现必须**可证伪**，登记到 Bugs 表时按此格式写「描述」列：

- 位置：`文件路径:行号`（无法定位行号时给出符号/段落名）
- 证据：最小代码片段或命令输出
- 断言：一句可证伪的话（「X 情况下会发生 Y」）

禁止概括式发现（如「错误处理不够完善」）——不能指出具体位置和触发条件的问题不予登记。

## git 基准规则

- `{milestone-start-ref}`：步骤1 写入里程碑文档 `## Context` 的 commit hash，唯一基准
- 变更范围一律用 `git diff --name-only {milestone-start-ref}` 获取
- **禁止裸 `git diff`**：步骤3 结束时变更已全部提交，裸 diff 结果为空 → 审查假通过
- **禁止用 git tag 作基准**：里程碑文档可能在 gitignored 目录，tag 可能不存在

## 审查职责切割

| 步骤 | 驱动 | 回答的问题 | 技能 |
|------|------|-----------|------|
| 2 设计核对 | 需求/设计驱动 | 设计是否符合产品文档与功能边界、是否合理 | `mdflow-review`（type=design） |
| 5 代码审查 | 标准驱动 | 代码是否符合审查维度（质量） | `mdflow-review`（type=code） |
| 7 功能验收 | 需求驱动 | 子任务/bug 说了要做的是不是真做了、有没有多做 | `mdflow-acceptance` |

步骤5 只管代码质量，步骤7 只管需求缺口，两者都从变更范围出发但产出不重叠。

## 报告清单

步骤2/4/5/6/7 的报告存放在 `.mdflow/milestones/{version}-reports/`（下列路径均相对于 `.mdflow/milestones/`）：

| 步骤 | 文件名 | 内容 |
|------|--------|------|
| 2 | `step2-design-review.md` | 里程碑文档 vs 产品文档的审查结论 |
| 4 | `step4-simplify.md` | 代码精简检查结果 |
| 5 | `step5-code-review.md` | 代码审查发现和严重程度分级 |
| 6 | `step6-test.md` | 测试命令运行结果和覆盖率 |
| 7 | `step7-acceptance.md` | 功能验收：代码实现 vs 里程碑文档的独立验证结论 |

- 报告只是证据，**不参与状态判断**（状态源见 SKILL.md 状态机）
- 打回不改名、不删除报告；下轮执行时覆盖同名文件

## 发现→规则沉淀

语义审查登记每条发现时附一问：**这类问题能否写成一条 grep 规则？**

- 能 → 在报告末尾「沉淀建议」段给出规则草案（匹配模式 + 期望），由维护者决定去向：可 grep 的入 `scripts/check.sh`（门禁本仓库）或目标项目 `AGENTS.md` 的 `## 代码审查维度`（步骤2/5 每轮必读，进维度即该项目每次审查生效）
- 不能 → 留在语义层，补充到目标项目 `AGENTS.md` 的 `## 审查维度`（步骤2）/`## 代码审查维度`（步骤5）

目的：同类问题第二次出现时由脚本拦截，审查成本逐次下降。
