# 平台投影（platform-sync.md）

## 定位

本文件是 **平台侧外壳的唯一详述来源**：mdflow 接入任务平台（如 Multica）时，平台承担哪些职责、以及平台与里程碑文档的分工边界。

**核心前提：里程碑文档是流程状态的唯一真相源，平台是只读投影 + 调度器。** 写方向永远是单向的 `文档 → 平台`，且只在步骤的 MARK 边界投影一次。平台侧的任何字段、状态、评论**都不参与**状态机的 GUARD 判断（见 `SKILL.md`「状态机」的「状态唯一来源」）。

## 为什么不做整体迁移（决策记录）

曾考虑把里程碑整体搬到平台任务上（子任务 = 子任务卡、Bugs 表 = 子任务卡），已否决。三条硬理由，每条单独都够否决：

1. **可移植性是一票否决项**。本技能集明确支持里程碑文档目录被 gitignore、纯本地单机可用（见 `SKILL.md`「Gitignore 处理」）。绑死某个平台工作区后，非该工作区的项目与纯本地用户直接不可用——可移植技能绑平台是不可逆的产品降级。
2. **平台任务状态写自带副作用**。将「设为进行中」类操作会立即触发执行者、状态变更会唤醒上级任务、失败还会自动回退状态。拿平台状态当 8 步状态机的刻度，每推进一步都可能误触发一次调度；文档勾选框是零副作用的。
3. **执行期机器锚点会失效**。沉淀建议表头按列名解析（契约「沉淀建议格式」）、报告按前缀读取（契约「报告清单」）、缺陷池写入行数配对（`mdflow-planner`）——这些 grep 锚点都长在 Markdown 文档里。搬到任务描述（无 git 历史、无同 commit、无 grep）之后，整条「发现→规则沉淀」管线会断。

## 职责边界

| 承载物 | 归属 | 说明 |
|--------|------|------|
| 流程状态（Flow Status、审查轮状态行、打回记录） | **里程碑文档** | 唯一真相源，不投影为机器可读结构 |
| 子任务详细设计、文件认领、依赖链 | **里程碑文档** | 依赖是稀疏的、按 `文件:行号` 重叠声明的单向链，不等价于平台的层级屏障 |
| Bugs 表 | **里程碑文档** | 批量轮审语义（轮内登记、轮末统一打回），且 `[x]` 行是步骤7「假修复」复核的证据链，不可被关闭态任务吞掉 |
| 审查轮 4/5/6/7 状态行 | **里程碑文档** | 一轮一个 4 元组三态，不拆成 4 个可独立流转的任务 |
| 报告目录、git 基准 `{milestone-start-ref}` | **里程碑文档 / 仓库** | 平台无对应概念 |
| 可见性（谁在做什么、进展如何） | **平台** | 父任务指针 + 汇报评论 |
| 调度（代替手工连续调用） | **平台** | 定时/条件唤醒代替 `/loop` |
| PR 关联 | **平台** | 提交信息带任务标识，平台自动关联 |

## 明确不做的事

- **不把 Bugs 表逐条变成平台任务**。Bug 是批量轮审语义（轮内登记、轮末统一打回，见契约「严重度分级契约」）；每建一个会立即触发执行者的任务等于把批量语义打碎，且关闭后丢失 `[x]` 证据行。如需团队可见，只在步骤8 汇报评论里贴统计数。
- **不把「依赖」字段机械翻译成层级分组**。依赖是稀疏的（无交集的子任务不写依赖，本来就可各干各的），层级分组是稠密的（同组全等、跨组全串行），硬翻译会制造假串行。平台只负责「屏障关闭时叫醒你」，依赖判断仍要读「依赖」字段。
- **不用平台状态驱动 GUARD**，也不用任务关闭态自动回勾文档。步骤7 功能验收的立身之本是「不信任 ⬜/✅ 标记、从 `git diff` 独立验证」；若文档勾选由平台完成态反向驱动，等于让验收信任它正要验证的东西，独立性就塌了。
- **不新建平台属性（property）作为必需依赖**。技能无权创建属性定义，依赖某个工作区预先建好的属性会让技能不可移植；已有属性可**可选**设置，不得作为流程推进的前提。
- **不做双向同步脚本**。单向投影 + 允许滞后已满足可见性需求；常驻同步本身会成为新的漂移来源。

## 投影动作

只有两个动作，二者都在失败时**静默跳过、不阻塞流程**（可移植性要求：无平台时技能必须完整可用）。

### 1. 步骤1：建立父任务指针

项目已在平台工作区内时，为当前里程碑建一个任务，作为可见性入口。描述只放**指针**，不复制正文：

```markdown
里程碑 {version}：{标题}

- 仓库：{repo}
- 里程碑文档：{milestone-path}
- 里程碑起始 ref：{milestone-start-ref}
```

要点：

- 指针信息取自里程碑文档 `## Context`（起始 ref 已在步骤1 写入），**不在此处另算基准**
- 描述里的文档路径是给人看的定位信息，**不参与**任何状态判断
- 描述**不复制**子任务清单、Bugs 表、审查轮状态行——那些留在文档里，避免两处副本各自漂移
- 项目不在平台工作区内、或平台不可用 → **跳过**，不提示错误、不中断步骤1

### 2. 步骤8：汇报评论 + 关闭父任务

步骤8 的「里程碑完成汇报」本身即一条平台评论的形状（见 `references/step8.md` 第 6 项）。发一条评论，内容为汇报正文，并把父任务置为完成态（若父任务曾创建）。

要点：

- 汇报内容仍以里程碑文档、Bugs 表与 git 记录为依据，**不凭对话记忆**；平台评论是汇报的**发布通道**，不是汇报的数据来源
- 评论里可贴 PR 链接（提交信息带任务标识即可自动关联），但**不得**把评论当验收证据——步骤7 的证据始终是 `round{N}/step7-acceptance.md`
- 平台不可用 → 跳过，步骤8 照常完成

## 调度：定时唤醒代替手工连续调用

`SKILL.md`「循环与上下文管理」的连续执行依赖平台内置的连续调用机制。项目已接入本平台时，改用平台的定时/条件唤醒代替手工 `/loop`：

- **定时唤醒**：按固定周期唤醒并调用本技能；每次调用从里程碑文档读取状态，自动执行下一步——因为状态在文档里，重复唤醒是幂等的
- **条件唤醒**优于定时：条件为「流程需要继续」时（当前步骤尚未勾选、审查轮状态行含 `—`、Bugs 表有 ⬜ 行）才唤醒，避免空转
- **投影不参与唤醒判定**：唤醒条件读的是里程碑文档，不是平台任务状态；两者不一致时以文档为准

## 冲突处理

| 情况 | 处理 |
|------|------|
| 文档与平台任务状态不一致 | **以文档为准**，平台允许滞后 |
| 投影动作失败（平台不可用、API 报错） | 静默跳过、不阻塞 MARK，不重试到成功 |
| 平台任务状态被人工改动 | 不回写文档；如与文档冲突，在下次汇报评论中说明以文档为准 |
| 用户要求以平台为准 | 明确告知这会破坏验收独立性（第 4 条「不做的事」），请用户确认后再偏离 |
