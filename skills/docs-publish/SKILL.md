# docs-publish：对外文档组织与发布

按 Diátaxis 四类组织项目对外文档，逐份复核真实性，再同步到 GitHub Wiki 与飞书。

**本技能不参与 mdflow 8 步状态机**：它是独立的发布动作，可与开发流程并行，不参与 Flow Status、不回退状态机。

**与 mdflow 的分工**：文档的**分类与发布**属本技能；文档与代码的**同步义务**（同仓同 commit）属 mdflow 契约「文档同步」，由步骤1/3/8 约束。

## 硬原则

1. **绝不自动生成内容** —— 只校验、索引、发布**已有**文档。虚构的文档比没有文档危害大：读者会照着不存在的命令操作。
2. **复核先于发布** —— 真实性复核未通过即**阻断发布**，不做「先发了再修」。
3. **推送前必须确认** —— 打印将要推送的文件清单，得到确认后才 `git push`（公开写操作不可逆）。
4. **缺失只提示、不阻断** —— 某类没有文档时报告「缺」，不视为违规；**漂移才阻断**。

## Diátaxis 四类

框架立场是**读者在某一时刻的需求**，不是文档讲什么。两组区分：

- **Tutorial + How-to** 讲用户**做什么**（行动）；**Reference + Explanation** 讲用户**知道什么**（认知）
- **Tutorial + Explanation** 服务**学习**；**How-to + Reference** 服务**应用**

**四类不可混写** —— 混写是成熟文档最常见的病（教程里插一段原理、参考文档里夹几行教学）。

| 类 | 读者需求 | 动作/认知 | 学/用 | 写法要求 |
|---|---|---|---|---|
| **Tutorial 教程** | 「带我做一遍」 | 行动 | 学习 | 有人带着走，读者只跟着做；**必须保证走通**，不解释原理、不给备选方案 |
| **How-to 指南** | 「帮我达成 X」 | 行动 | 应用 | 目标导向，假定读者已会基本；**不教原理**，直接给达成路径 |
| **Reference 参考** | 「查一下」 | 认知 | 应用 | 只描述机器：签名、参数、取值、错误码；**不解释、不教学、不给步骤** |
| **Explanation 解释** | 「为什么是这样」 | 认知 | 学习 | 讲背景、理由、取舍、权衡、限制来源；**不给操作步骤** |

**混写检测**（发布前逐份问）：
- 教程里出现「这是因为…」的原理段落 → 拆出去归 Explanation
- 参考文档里出现「第一步、第二步」→ 拆出去归 How-to
- How-to 里反复解释「为什么这样设计」→ 拆出去归 Explanation

### 路径约定

| 类 | 推荐路径 |
|---|---|
| Tutorial | `docs/tutorials/` |
| How-to | `docs/how-to/` |
| Reference | `docs/reference/` |
| Explanation | `docs/explanation/` |
| 门面（**不属四类**） | `README.md` |

**README 是索引与定位，不是一类文档** —— 它回答「这是什么 / 从哪开始」，不承载任何一类的实质内容。

**路径可裁剪可映射，不强制改名** —— 强制改名会破坏既有链接。项目已有等效结构时按实际映射，映射关系在回复中列出。

### 按产品类型调配比

**四类对所有产品都成立，变的只是权重**。不是三套结构，是一个结构的配比参数（`--profile`）：

| Profile | 适用 | 重心与特点 |
|---|---|---|
| `cli` | CLI / TUI / 库 | **Reference 为主**（命令全集、配置项、快捷键），Tutorial 次之；几乎无 Explanation；**无部署运维内容**（装个二进制即完成） |
| `service` | 容器化 / 服务端应用 | How-to（业务任务）+ Tutorial（起一套并验证）；Explanation 给权限/加密决策；运维内容（升级/备份/多实例）并入 How-to 或独立成册 |
| `platform` | 自托管 / 客户端-服务端 | 四类齐全；**特有风险：双端版本兼容性矩阵必须显式**；Explanation 承载协议设计；排障路径与日常操作路径分开写 |

探测不确定时**问用户**，不猜 —— 配比判断错了整套校验重心会错。

### 第二维：产品分组

产品线多时，在四类内部按产品/模块再分一层（如 `docs/how-to/ssh/`、`docs/reference/api/`）。

**判定何时分组**：某产品线的文档 ≥3 份、且读者只会关心其中一条线时才分。文档量小时保持单层线性 —— 过深的导航层级比过平更糟。

## 排除区（不发布、不对外）

| 类别 | 实例 | 原因 |
|---|---|---|
| 流程产物 | `AGENTS.md`、`CHANGELOG.md`、`docs/BUGS.md`、`docs/DEVELOPMENT.md`、`docs/PRODUCT.md` | 内部状态与术语；`PRODUCT.md` 含 `[待规划]/[已规划]` 标记，直接发布会让外部读者看到未建成功能 |
| 第三方子模块自带文档 | 内嵌子项目的 README/CHANGELOG | 不是本产品文档，会误导读者以为是本产品功能 |
| 过程材料 | 调研笔记、路线图、backlog | 对外无价值 |

**发布判定逐份按受众，不按目录一刀切**：同在 Explanation 目录下，协议设计可发布而某个模块的实现细节不发布。判定问句 —— **「这份文档的读者，会在本次发布目的之外继续用它吗？」** 会 → 发布。

## 四条检查项（与分类正交，逐份跑）

这是对外文档真正的 spec。业界产品文档的失败模式几乎都落在这四条上。

### 准确

| 检查 | 判定依据 | 实测漂移样例 |
|---|---|---|
| 引用的命令存在 | `package.json` scripts / `Makefile` 目标 / `scripts/` 文件 / CLI 框架的命令定义 | 某项目加密文档写 `check_keys.sh`，仓库无此文件 |
| 引用的仓库内路径存在 | 文件系统实际存在 | 某项目测试文档写 `github/workflows/ci.yml`，仓库无 `.github/` |
| 版本号对账 | 文档声明 == 依赖清单实际值 | — |
| 接口与错误码对账 | 逐条对代码（签名、枚举值、错误码全集） | — |
| 数值型断言有来源 | 「支持 N 并发」须指向压测记录或配置项 | — |
| 对外安全承诺可验证 | README 承诺的属性（加密、隔离、审计）须有对应安全文档且**互链** | 某自托管项目 README 承诺加密隧道却未链到加密文档 |

### 易懂

- **术语一致**：同一概念全文只用一个词（禁止「Agent 代理」/「智能体」混用）
- **首次出现处给定义**：专有名词在文档内首次出现处定义，且与代码实际命名一致
- **内部黑话零出现**：里程碑、Flow Status、审查轮、缺陷池、`[待规划]` 等术语不得出现在对外文档
- **主动澄清歧义**：易误解的命名要显式说明（如「Hub 指用户侧服务端，不泛称中枢」—— 实测有项目自发这样做，说明写作者吃过术语不准的亏）

### 可操作

How-to 与 Tutorial 里每个操作段落必须四要素齐全，缺任一即标记「不可操作」，发布前补齐：

```
前置条件 → 命令 → 预期输出 → 失败怎么办
```

**Reference 与 Explanation 不适用**（它们本就不提供操作步骤）—— 四要素检查只作用于行动类文档。

### 可关联

- 每份文档头部有**面包屑**（属于哪一类、在哪）
- 相对链接**必须解析到真实文件**（实测有项目文档 5 份、相对链接 0 条 —— 直接不达标）
- 相关文档**双向互链**（A 提到 B，B 能回指 A）
- Tutorial 末尾必须链到 How-to 的对应任务

## L1 复核：机器可判（快速筛）

只作用于**行动类文档**（Tutorial / How-to）里的可执行指令。

| 校验项 | 判定依据 |
|---|---|
| 命令存在性 | `package.json` scripts / `Makefile` 目标 / `scripts/` 目录 / CLI 框架命令定义 |
| 仓库内路径存在性 | 文件系统实际存在 |

### 强制豁免（不校验，防误伤）

**不加豁免会假红 70+ 处** —— 实测教训：

- **外部仓库引用** —— 调研笔记引用其他项目的源码路径，天然不在本仓库
- **历史记录** —— `DEVELOPMENT.md` 里程碑描述、`CHANGELOG` 记录的是「当时做过」，文件可能已改名或删除
- **示例与占位值** —— 明显是示例的值（`YOUR_*` / `EXAMPLE_*` / `localhost`）
- **runbook 里「教读者创建」的脚本** —— 文档用 ` ```bash ` 代码块**给出脚本内容**（运维手册常见写法：把脚本贴给读者复制到本地跑），文档声称的是「脚本该长什么样」，不是「仓库里有这个文件」。判据：**该 token 出现在代码块内且带 shebang** → 豁免；出现在正文声称「运行 `xxx.sh`」→ 才算漂移。
  > 实测踩过：某项目加密 runbook 引用 `check_keys.sh`、`key_version_stats.sh`，两个文件仓库里都不存在，一度判为漂移。核实后确认前者是代码块里给出完整脚本内容、后者原文写着「建议把它落到本地」——**是教创建，不是声称存在**。假红比漏红更贵：它让人去「修」根本没坏的文档。
- **backtick 内「路径 + 参数」拼接** —— `` `scripts/check-coverage.sh 98` `` 是一个反引号里塞了路径和阈值两个 token，**不能整串当路径去 `exists()`**。判据：含空格的引用**先按空白切分**，只对疑似路径的那一段做存在性检查。
  > 同一次实测踩过：`scripts/check-coverage.sh` 文件确实存在（868B 可执行），却因整串判不存在而假红。

## L2 复核：读代码（核心）

L1 只能确认「路径在不在」，**不能确认「文档说的机制与代码一致」**。L2 是本技能的核心。

对每个能力类断言、Reference 条目、Explanation 中的机制描述：

1. 在代码中定位**实际实现点**，记录 `文件:行号`
2. 比对差异：函数名、调用链、配置键读取方式、错误码、默认值、依赖版本
3. 输出证据表：

| 文档断言 | 出处 | 代码位置 | 判定 | 差异 |
|---|---|---|---|---|
| 日志级别由 `RUST_LOG` 控制 | `docs/how-to/logging.md` | `src/observ.rs:42` | ✓ 一致 | — |
| 租户隔离依赖某环境变量 | `docs/explanation/tenant.md` | 未找到读取点 | ★ 漂移 | 代码中无该读取，能力可能未实现或已改名 |

**复核深度**：默认只对「产品能力」与「运维可执行指令」做代码定位；`--deep` 对全部断言逐条定位。

### 误判陷阱（实测踩过，务必遵守）

- **不要用「全大写下划线」判定环境变量** —— 会把错误码常量、SQL 类型、迁移常量、协议常量全部误报。必须看代码里 `env::var` / `process.env` / `EnvFilter` 等**实际读取点**。实测此误报产生 97 个假阳性。
- **间接读取要追到底** —— `EnvFilter::from_default_env()` 隐式读 `RUST_LOG`，直接 grep `env::var` 会漏。
- **多包仓库的命令要标作用域** —— 混合仓库顶层的构建命令只在子包成立，文档须注明工作目录，否则按漂移处理。
- **斜杠连写的多个 script 不是合法命令** —— 形如 `type-check/lint/build` 的写法应直接判漂移。

## 执行步骤

### 1. GUARD：解析配置

- 文档根：读 `AGENTS.md` 找文档目录约定（默认 `docs/`），未定义则用 `docs/`
- 产品类型：按依赖清单与分发文件探测（有无 Dockerfile/compose → `service`；有无 CLI 框架 + TUI 库 → `cli`；多可执行文件 + 客户端-服务端语义 → `platform`）；**判不准时问用户**
- 远端：`git remote get-url origin`，推导 Wiki URL（`git@github.com:OWNER/REPO.git` → `https://github.com/OWNER/REPO.wiki.git`）
- 凭证：探测 `FEISHU_APP_ID`/`FEISHU_APP_SECRET`；`GITHUB_TOKEN`（可选，公开仓库免 token）
- **凭证缺失不终止，按三级降级**：① 本地已有可推送飞书的技能（`~/.config/opencode/skills/` 下任一声明能写飞书文档的技能）→ **委派给它**，由它持有凭证与通道，本技能只交付 Markdown 与目标结构；② 无此技能但用户在场 → 问用户要凭证或指定技能，**不自行索要密钥入 env**；③ 都没有 → 标「跳过（无可用推送通道）」，继续 GitHub Wiki，**不报错、不阻断**

### 2. 结构校验

按四类逐项探测：命中推荐路径 → 归位并统计文件数；未命中 → 尝试识别等效目录；仍无 → 记「**缺**」。

同时做**混写检测**（见上），标出疑似跨类内容。

输出：类 | 路径 | 文件数 | 状态（有/缺）+ 疑似混写清单。

**索引检查**：文档根须有一份索引（默认 `docs/README.md`，以 `AGENTS.md` 为准）。缺失时生成索引页 —— 索引是**导航骨架**，不属于「自动生成内容」豁免范围。已有索引则只校验链接指向的文件是否存在，不重写。

### 3. L1 + L2 复核

见上两节。

### 4. 汇总与裁决

| 判定 | 含义 | 处置 |
|---|---|---|
| ✓ 一致 | 有代码位置佐证 | 通过 |
| ★ 漂移 | 文档与代码不符 | **阻断发布**，列待裁决项：改文档 / 改代码 / 标注废弃 |
| ⌀ 缺 | 某类无文档 | 提示，不阻断 |
| ⚠ 混写 | 疑似跨类内容 | 提示拆分建议，不阻断 |

**产物形态**：证据表默认只回显。`--save-audit` 时落盘 `{文档根}/.publish-audit.md`，便于事后追溯与复查。

### 5. 发布：GitHub Wiki

前置：GitHub Wiki **默认关闭**，需用户在仓库 Settings 启用，技能无法绕过。

```bash
wiki_url="https://github.com/OWNER/REPO.wiki.git"
workdir=$(mktemp -d)
git clone --depth 1 "$wiki_url" "$workdir"
```

映射：`README.md` → `Home.md`；四类 → 各目录下同名文件夹；`_Sidebar.md` 按四类生成分组导航（不按第二维平铺）。

**推送前必须打印清单并等确认**：

```
将要推送到 REPO.wiki：
  新增  Home.md
  新增  _Sidebar.md
  修改  how-to/ssh/README.md
  删除  reference/legacy.md
确认推送？(y/N)
```

### 6. 发布：飞书

**先委派，后自建**：本地已有可推送飞书的技能时，**优先委派**——把 Markdown 正文 + 目标目录结构交给它，由它负责凭证、鉴权与写入。本技能不重复实现鉴权，也不把密钥读进自己的上下文。委派时须交付：

| 交付项 | 内容 |
|---|---|
| 正文 | 按 Diátaxis 分类好的 Markdown（未经改写的原文） |
| 目标结构 | 文档根、每篇的分类归属、页面标题层级 |
| 映射约定 | 与 GitHub Wiki **同一套**文件名映射，避免两处命名分叉 |

**没有可委派技能时**才自建通道，凭证 `FEISHU_APP_ID` + `FEISHU_APP_SECRET`（或 `FEISHU_TENANT_ACCESS_TOKEN`）：

```
POST /open-apis/auth/v3/tenant_access_token/internal   换 token
POST /open-apis/docx/v1/documents                        建文档
POST /open-apis/docx/v1/documents/{id}/blocks            写块
```

无 SDK 时用 stdlib `urllib` 即可，不要为一次推送引入依赖。

**Markdown → block 转换（最小可用）**：支持标题、段落、有序/无序列表、代码块；表格降级为纯文本行。**不支持的语法原样保留为段落并在报告中标记**，绝不静默丢内容。

> 已知取舍：表格降级损失列对齐。可选改进：调飞书表格块 API 精确还原。当前先保证「不丢内容」。

## 参数

| 参数 | 作用 |
|---|---|
| `--check` | 只做结构校验 + 两级复核，不推送 |
| `--target wiki\|feishu\|both` | 指定发布目标（默认 `both`） |
| `--profile cli\|service\|platform` | 指定产品类型配比；不传则自动探测，判不准时问用户 |
| `--deep` | L2 逐条断言定位（默认只做能力类与运维指令） |
| `--save-audit` | 证据表落盘到 `{文档根}/.publish-audit.md` |
| `--force` | 有漂移时仍继续发布（默认阻断，须用户显式给出） |
