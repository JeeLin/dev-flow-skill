# dev-acceptance：功能验收（独立审查）

本技能提供**独立于开发阶段**的功能验收机制。核心原则：从代码变更和客观证据出发，逐项验证需求是否真正满足，不依赖任何流程标记或开发者自述。

## 适用场景

| 场景 | 调用方 | 验收对象 | 输出报告 |
|------|--------|----------|----------|
| 功能验收（开发后） | dev-flow 步骤7 | 已实现代码 vs 里程碑文档 | `step7-acceptance.md` |

## 核心约束（硬规则）

本技能的验证逻辑受以下硬规则约束，**不可妥协、不可绕过**：

### 1. 从 git diff 出发，作为唯一入口

验收必须从 `git diff {milestone-start-ref}` 获取变更文件列表，以此为起点逐文件审查。不得跳过 diff 直接"凭印象"判断。

### 2. 不信任流程标记

里程碑文档中的 ✅/[x] 标记**仅表示流程状态**（开发者自认为完成），**不是验证依据**。验收时：

- 不以子任务状态列的 ✅ 作为"已实现"的证据
- 不以 Bugs 表格中的 [x] 作为"已修复"的证据
- 每个子任务和 bug 必须独立验证，无论标记如何

### 3. 不引用步骤 3 的提交信息

步骤 3 的 commit message 是开发者的自述，不是客观证据。验收时：

- 不引用任何 commit message 作为"已实现"或"已修复"的依据
- 不检查 commit 历史来判断完成度
- 唯一信任的证据来源：**git diff 的实际代码变更** 和 **命令输出（测试/编译/lint）**

### 4. 逐项验证，不概括

每个子任务和每个已修复 bug 必须单独验证，给出独立结论。不允许"整体看起来没问题"式的概括判断。

## 严重度分级

验收中发现问题时，按以下标准分级后登记到里程碑文档的 Bugs 表格：

| 级别 | 含义 | 验收中的判定场景 |
|------|------|------------------|
| 🔴 必须修复 | 需求未满足 | 子任务功能未实现、核心接口与设计不一致、bug 修复缺失或无效、关键逻辑错误 |
| 🟡 应该修复 | 实现细节问题 | 功能已实现但细节偏差（命名/格式/非关键路径逻辑）、测试覆盖缺失但功能本身正确、非阻塞性质量问题 |

验收中**不使用** 🟢——验收只判断"需求是否满足"，风格优化类问题属于步骤4（代码精简）和步骤5（代码审查）的范畴。

## Bug → diff 映射方法

Bugs 表格中的 bug 描述是自然语言，验收时需要定位对应的代码变更。映射策略（按优先级尝试）：

1. **按来源定位**：bug 的"来源"列通常标明了引入阶段（如"步骤5代码审查"），结合子任务编号缩小范围
2. **按标题关键词匹配**：从 bug 标题和描述中提取关键词（函数名、文件名、模块名），在 diff 中搜索匹配的文件和变更
3. **按影响范围推断**：根据 bug 描述的"现象"（如"登录页面表单提交后未重置"），推断涉及的文件路径，在 diff 中查找该文件的变更
4. **映射失败时**：若无法从 diff 中找到对应修复代码，在验收报告中标记为 ❌（修复缺失），来源列注明"无法定位修复代码"

## 验收流程

### 0. 准备

1. 读取里程碑文档，获取：
   - 子任务清单（`## 子任务清单`）
   - 子任务详细设计（`## 子任务详细设计`）
   - Bugs 表格（`## Bugs`）中状态为 [x] 的已修复项
2. 获取变更文件列表：`git diff --name-only {milestone-start-ref}`
3. 获取实际 diff 内容：`git diff {milestone-start-ref}`（按文件分段读取）

### 1. 子任务验收

对里程碑文档中的每个子任务：

1. **定位变更**：从 diff 中找到该子任务涉及的文件和代码变更
2. **逐项验证**：对照详细设计中的功能目标、接口设计、交互设计，检查代码变更是否真正实现了对应功能
3. **独立结论**：每个子任务给出 ✅（已满足）/ ❌（未满足/部分满足），并说明具体证据（引用 diff 中的文件和行号）
4. **❌ 时标注**：未满足的具体点和差距

验证维度（按子任务详细设计逐项核对）：

| 维度 | 检查内容 |
|------|----------|
| 功能目标 | 代码变更是否实现了详细设计中描述的功能 |
| 接口设计 | API 端点 / 组件 props / 数据模型是否与设计一致 |
| 后端流程 | 处理逻辑是否覆盖了设计中的流程描述 |
| 测试标准 | 是否有对应测试覆盖（检查测试文件变更） |

### 2. Bug 修复验收

对 Bugs 表格中状态为 [x] 的每个 bug：

1. **定位修复**：从 diff 中找到该 bug 对应的代码变更
2. **验证修复**：检查修复是否真正解决了问题描述中的场景，而非仅修改了表面
3. **独立结论**：每个 bug 给出 ✅（已修复）/ ❌（未修复/修复不完整），并说明具体证据
4. **❌ 时标注**：修复不完整的具体点

### 3. 未覆盖检查

检查是否存在以下情况：

- 里程碑文档中定义了功能，但 diff 中**无对应代码变更**（子任务可能未实现）
- Bugs 表格中标记 [x]，但 diff 中**无对应修复代码**（bug 可能未真正修复）
- diff 中存在**里程碑文档未定义的变更**（可能是范围外变更，需标注）

### 4. 生成验收报告

报告写入 `{version}-reports/step7-acceptance.md`。

## 报告模板

```markdown
# 功能验收：{里程碑版本}

## 验收原则

- 从 git diff ({milestone-start-ref}) 出发，逐文件审查
- 不信任 ✅/[x] 流程标记
- 不引用步骤 3 的提交信息
- 每个子任务和 bug 独立验证

## 变更概览

- **变更文件**：{数量}
- **基准 ref**：{milestone-start-ref}
- **验收时间**：{时间}

## 子任务验收

| # | 子任务 | 结论 | 证据 | 说明 |
|---|--------|------|------|------|
| 1 | {子任务标题} | ✅/❌ | {涉及文件} | {说明} |
| 2 | {子任务标题} | ✅/❌ | {涉及文件} | {说明} |

## Bug 修复验收

| # | 优先级 | 标题 | 结论 | 证据 | 说明 |
|---|--------|------|------|------|------|
| 1 | 🔴/🟡 | {bug 标题} | ✅/❌ | {涉及文件} | {说明} |

## 未覆盖检查

- ✅ 无遗漏子任务
- ✅ 无遗漏 bug 修复
- ✅ 无范围外变更（或已标注）

## 汇总

- **子任务通过**：{N}/{总数}
- **Bug 修复通过**：{N}/{总数}
- **结论**：✅ 验收通过 / ❌ 验收不通过
```

## 通过标准

- 所有子任务结论为 ✅
- 所有已修复 bug 结论为 ✅
- 无遗漏子任务或 bug 修复
- 以上全部满足 → ✅ 验收通过；任一不满足 → ❌ 验收不通过

## 使用方式

dev-flow 步骤7调用本技能时，需提供：

1. **里程碑文档路径**：包含子任务清单、详细设计、Bugs 表格
2. **里程碑起始 ref**：步骤1 打上的 `milestone-{version}-start` tag
3. **agents_md 路径**：项目约定文件，验收中参考技术栈、代码规范等
4. **报告路径**：`{version}-reports/step7-acceptance.md`

本技能负责：
- 从 git diff 出发获取变更证据
- 逐子任务和逐 bug 独立验收
- 生成验收报告并计算结论
- 返回验收结果：
  - `conclusion`：✅ 验收通过 / ❌ 验收不通过
  - `report_path`：验收报告文件路径
  - `issues`：问题列表（每个问题含 `target`（子任务编号或 bug 标题）、`severity`（🔴/🟡）、`description`（具体差距和证据））
