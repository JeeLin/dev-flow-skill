# dev-bug：记录 Bug

将用户报告的 bug 写入当前里程碑文档的 Bugs 表格，或显式移除缺陷池中已修复的 bug。

## 输入

- **记录**：`/dev-bug <描述>` —— 将 bug 写入当前里程碑 Bugs 表或缺陷池（见执行步骤）。
- **关闭**：`/dev-bug close <关键词>` —— 缺陷池中匹配关键词的 bug 已修复，从 `docs/BUGS.md` 删除对应行（见「关闭缺陷池 bug」）。

## 执行步骤

1. **定位当前里程碑**：
   - 读取 `AGENTS.md` 获取里程碑目录路径（默认 `docs/milestones/`）
   - 列出目录下所有 `.md` 文件（报告文件都在 `-reports/` 子目录中，递归排除该子目录即可，包括被重命名为 `.rejected` 的旧报告）
   - 从文件名提取版本标识（支持 `v{X.Y.Z}-{name}.md` 语义版本风格与 `M{数字}-{name}.md` 序号风格），按标识排序取最大
   - 读取该最大标识里程碑的 `## Flow Status` 段落：若仍存在 `[ ]`（未勾选）步骤，即为当前里程碑；若全部勾选，提示用户当前版本已完成，先执行 dev-flow 创建新里程碑
   - 注意：步骤3 完成后用户可能通过 `/dev-bug` 中途报告 bug，此时步骤3 已勾选但仍属当前里程碑，故以「最大标识且未完成」为准，而非「第一个存在未勾选步骤」
2. **解析 bug 描述**：
   - **标题**：从描述中提取一句话概括
   - **优先级**：级别语义与处置见 dev-flow 技能「严重度分级契约」；本入口（用户反馈视角）特有判定关键词：
     - 🔴 崩溃/无法使用/数据丢失/接口报错/阻塞性问题
     - 🟡 偶发/功能异常/体验问题/非阻塞性问题
     - 🟢 建议优化/锦上添花/轻微问题
3. **归属核对（边界检查）**：
   - 读取当前里程碑文档的 `## 产品边界` 与 `## 子任务清单`，了解本里程碑的覆盖范围。
   - **仅当 bug 描述明显涉及当前里程碑范围之外时**才提醒（例如：当前里程碑只涉及前端，但 bug 描述明显指向后端/API/数据库/服务端）。判断要宽松，正常情况（用户主动报的、无法明确判定越界的）直接视为属于当前里程碑，不要频繁打断。
   - 若判定明显越界，向用户确认归属：
     - 用户选择「属于当前里程碑」→ 按步骤4 写入当前里程碑的 `## Bugs` 表（遵循"主动提交的 bug 即属于当前里程碑"原则）。
     - 用户选择「加入缺陷池（下个版本）」→ 按步骤5 写入 `docs/BUGS.md` 缺陷池，不写入当前里程碑、不触发 dev-flow 状态机回退。
4. **写入当前里程碑 Bugs 表格**（归属为当前里程碑时）：在里程碑文档的 `## Bugs` 表格末尾追加一行：

   ```
   | ⬜ | {优先级} | {标题} | 用户反馈 | {描述} |
   ```

5. **写入缺陷池**（归属为下个版本时）：追加到 `docs/BUGS.md`（若该文件不存在则新建，格式见下方「缺陷池格式」）：

   ```
   | {当前里程碑版本} | {优先级} | {标题} | 用户反馈 | {描述} |
   ```

   第一列记录"提出时所处里程碑版本"，便于下个版本规划时回溯来源。

6. **回复确认**：显示写入的内容，格式如：

   ```
   ✅ 已记录（当前里程碑）
   - 优先级：🟡
   - 标题：登录接口偶发 500
   - 描述：用户登录时偶尔返回 500 错误，刷新后正常
   ```
   若写入缺陷池，则回复：「✅ 已记录为下个版本待处理（缺陷池 docs/BUGS.md）」。

## 关闭缺陷池 bug（close 模式）

当缺陷池（docs/BUGS.md）中的某条 bug 已被顺手修复、或经其他途径解决，而尚未被 `milestone-planner` 纳入下一个里程碑时，可显式将其从缺陷池移除：

1. 确认 `docs/BUGS.md` 存在；若不存在，提示用户「缺陷池为空，无可关闭项」。
2. 在缺陷池表格中按 `<关键词>` 匹配（标题、描述、来源列均可匹配），定位目标行。
3. 若匹配到**唯一一行** → 删除该行，回复：「✅ 已从缺陷池移除：{标题}」。
4. 若匹配到**多行** → 列出所有匹配行供用户确认要删除哪一行（或一并删除），避免误删。
5. 若**未匹配到** → 回复：「未找到匹配『{关键词}』的缺陷池条目」。

**原则**：关闭即删除整行，与 `milestone-planner` 纳入时的删除动作一致——缺陷池只用「在不在表里」表示是否待处理，不引入额外状态列。池子清空后保留文件头（空表）即可，不必删除文件。

## 缺陷池格式

`docs/BUGS.md`（默认路径，以 `AGENTS.md` 定义为准）统一收集"加入缺陷池（下个版本）"的 bug，由 `milestone-planner` 规划下一个里程碑时吸纳。文件结构：

```markdown
# 缺陷池

| 提出版本 | 优先级 | 标题 | 来源 | 描述 |
|----------|--------|------|------|------|
| v0.2.0 | 🟡 | 登录接口偶发 500 | 用户反馈 | 用户登录时偶尔返回 500 错误 |
```

优先级取值与里程碑 Bugs 表一致，级别语义见 dev-flow 技能「严重度分级契约」。

## 注意事项

- 来源固定为「用户反馈」
- 写入当前里程碑 Bugs 表的条目状态列默认填 ⬜，由 dev-flow 步骤3 处理后改为 [x]
- 如果有多个 bug，逐条分别写入
- 写入缺陷池的 bug **不属于**当前里程碑，不会触发 dev-flow 状态机"回到步骤3 修复"的回退逻辑
- 缺陷池条目有两种移除途径：① 被 `milestone-planner` 规划进下一个里程碑时删行转入该里程碑 Bugs 表；② 已修复时由 `/dev-bug close <关键词>` 显式删行。缺陷池只用「在不在表里」表示是否待处理
